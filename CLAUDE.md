# AI Automation Architect — контекст проекта

## Что это

Мини-система, которая превращает свободное текстовое описание бизнес-процесса в структурированный **Automation Blueprint** (JSON) — с картой процесса, оценкой автоматизируемости каждого шага и предлагаемой архитектурой. Из JSON фронт рендерит карточки и диаграммы (Mermaid).

Портфолио-проект для B2B-позиционирования: демонстрирует не только код, но и способность переводить бизнес-проблему в техническое решение.

**Пример входа:**
> «У нас 50–100 заявок в Telegram в день. Менеджер вручную переносит их в таблицу, определяет тип клиента, отвечает на типовые вопросы и передаёт сложные обращения руководителю».

**Выход:** Automation Blueprint — JSON с процессом, шагами, % автоматизации каждого шага, архитектурой из типовых блоков, рисками и MVP-scope.

## Область MVP (важно!)

**Входит в MVP:**
1. Business Process (шаги, актёры, входы/выходы)
2. Automation Opportunities (таблица: шаг → категория → % автоматизации)
3. Architecture (граф из фиксированного каталога блоков)
4. Упаковка в финальный JSON + risks / mvp_scope / estimated_effort

**НЕ входит в MVP (v2):**
- Генерация полного технического задания: API endpoints, модели данных, тест-сценарии, error handling как отдельные артефакты. Это отдельный модуль поверх готового blueprint, делаем только после того, как ядро отработано на реальных кейсах.

Не пытайся реализовать v2-фичи «заодно» — они размывают фокус и первыми проседают по качеству.

## Архитектура пайплайна — 4 отдельных LLM-вызова, не один промпт

Ключевой принцип проекта: **риск в достоверности выходов снимается таблицами/каталогами, а не доверием к LLM.** LLM классифицирует и компонует, а не изобретает цифры и архитектуру с нуля.

### Stage 1 — Process Extractor
Извлекает `actors`, `entry_point`, `steps` (id, name, input, output, actor) строго из текста описания. Не додумывает шаги — если что-то неоднозначно, помечает в `assumptions`, а не выбирает молча.

### Stage 2 — Classifier
Классифицирует каждый шаг по **фиксированной taxonomy-таблице** (см. `config/taxonomy.yaml`), не изобретая категории. Процент автоматизации берётся из диапазона категории, а не подбирается моделью произвольно.

Taxonomy (базовая версия, редактируется в конфиге, не в промпте):

| Категория | Диапазон % |
|---|---|
| Приём/сбор данных (вебхук, входящее сообщение) | 95–100 |
| Извлечение структурированных данных (парсинг, NER) | 85–100 |
| Классификация / маршрутизация | 80–95 |
| Типовой ответ (FAQ, RAG) | 70–90 |
| Генерация персонализированного контента | 50–75 |
| Оценка неоднозначного случая / суждение | 20–50 |
| Переговоры, эмоционально чувствительное общение | 0–30 |
| Решение с юридическими/финансовыми последствиями | 0–20 |

### Stage 3 — Architecture Composer
Собирает архитектуру **только** из блоков каталога (см. `config/block_catalog.yaml`): `Bot/Webhook Receiver, Data Extractor (LLM), Classifier/Router, RAG Responder, Generator (LLM), Rules Engine, CRM Connector, Notifier, Human Escalation`. Не создаёт новые типы блоков. Возвращает граф `nodes` + `edges`.

### Stage 4 — Blueprint Packager
Собирает выходы стадий 1–3 в финальную схему + генерирует `risks`, `mvp_scope`, `estimated_effort` (это advisory-часть, здесь LLM может рассуждать свободнее — не факты, а рекомендации).

**Правило для любой стадии:** валидировать выход через Pydantic-схему сразу после вызова, при невалидном JSON — retry с уточняющим промптом, не пытаться "починить" руками в коде.

## Финальная схема Blueprint

```json
{
  "process": "string",
  "actors": ["string"],
  "steps": [
    {"id": "string", "name": "string", "input": "string", "output": "string", "actor": "string"}
  ],
  "automation_candidates": [
    {"step_id": "string", "category": "string", "automation_pct": 0, "reasoning": "string"}
  ],
  "architecture": {
    "nodes": [{"id": "string", "block_type": "string", "step_ids": ["string"], "note": "string | null"}],
    "edges": [{"from": "string", "to": "string"}]
  },
  "human_in_the_loop": ["step_id"],
  "integrations": ["string"],
  "risks": ["string"],
  "mvp_scope": {"in": ["string"], "out": ["string"]},
  "estimated_effort": {"component": "человеко-дни"}
}
```

Держи эту схему как единый источник правды (Pydantic-модели в `app/schemas.py`) — на неё завязаны все 4 стадии и фронт.

## Технологический стек

Соответствует остальным проектам в портфолио — не вводи новый стек без причины:

- **Backend:** FastAPI (async), Pydantic v2 для схем и валидации
- **LLM:** OpenAI-совместимый клиент через ProxyAPI (`PROXYAPI_BASE_URL`), модель задаётся в `LLM_MODEL` (по умолчанию gpt-4o-mini) — не хардкодить модель и base_url в коде. Stage 1 работает на отдельной модели `LLM_MODEL_STAGE1` (по умолчанию — `LLM_MODEL`): более сильная модель нужна Stage 1 из-за задач семантической интерпретации (channel/criteria-детекция); Stage 2/3 работают на базовой модели без проблем. Температура Stage 1 переопределяется `LLM_TEMPERATURE_STAGE1` (по умолчанию 0.1). Structured output через `response_format` / function calling (OpenAI tool-calling), не через Anthropic-специфичный tool_use. Остальные параметры вызова (`LLM_TEMPERATURE` — базовая для Stage 2/3, `LLM_TIMEOUT_S`, `LLM_MAX_TOKENS`) — тоже из окружения.
- **Рендеринг диаграмм:** Mermaid (process flow + architecture graph) — генерируется из JSON на бэке или фронте
- **Конфиги:** `config/taxonomy.yaml`, `config/block_catalog.yaml` — редактируемые без правки кода
- **Хранение примеров:** `examples/` — заранее прогнанные и сохранённые кейсы для демо, разложены по уровню пайплайна: `raw/` (исходные тексты описаний), `extracted/`, `classified/`, `architecture/` (выходы Stage 1–3), `blueprints/` (финальные Automation Blueprint — готовые кейсы для фронтенда)
- **Деплой:** Docker + VPS, как в остальных проектах
- **Логирование:** логировать вход/выход каждой стадии отдельно (для отладки пайплайна и как демонстрация внимания к observability)

## Конвенции разработки

- Каждую стадию пайплайна разрабатывать и тестировать **отдельно**, прежде чем собирать в общий пайплайн — иначе непонятно, на какой стадии теряется качество.
- Тестировать не только "счастливый путь": подавать двусмысленные/неполные описания процессов и проверять, что `assumptions` заполняется, а не придумываются шаги.
- Категории (Stage 2) и типы блоков (Stage 3) — enum, а не свободная строка. Любое значение вне списка = ошибка валидации, а не "почти похоже, сойдёт".
- Не хардкодить taxonomy/каталог в промпт-тексте — подставлять из конфигов, чтобы их можно было менять без деплоя нового промпта.
- Перед показом кому-либо — прогнать все `examples/*.json` заново и убедиться, что вывод стабилен между запусками (temperature низкий на стадиях 1–3, чуть выше допустим только на Stage 4 для risks/mvp_scope).
- Все текстовые/YAML файлы читать с encoding='utf-8-sig' (Windows-инструменты часто добавляют BOM) — 'utf-8' без -sig может некорректно разобрать первый символ.

## Что не делать

- Не позволять модели придумывать процент автоматизации вне диапазона его категории — это ломает главный аргумент доверия к проекту.
- Не позволять модели изобретать новые архитектурные блоки — диаграмма должна быть предсказуемой между разными кейсами.
- Не тащить TZ-генерацию (endpoints/models/tests) в MVP — см. раздел «Область MVP».
- Не публиковать демо без заранее прогнанных `examples/` — случайный плохой инпут от посетителя не должен быть первым впечатлением от проекта.

## Известные ограничения

- Stage 1 не детектирует неявное ветвление, если оно не выражено явным условием в тексте (пример: «Определение типа клиента» без описанных исходов классифицируется как линейный шаг). Обходится тем, что критерии эскалации/сложности в текстах обычно явные и детектируются корректно.
