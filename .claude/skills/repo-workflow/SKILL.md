# ai-automation-architect — рабочий процесс

Проект: свободный текст бизнес-процесса → Automation Blueprint (JSON) через пайплайн из 4 LLM-стадий. Портфолио-проект для B2B-позиционирования.

**Архитектура, конвенции пайплайна, границы MVP и Known Limitations — в `CLAUDE.md`, это источник правды.** Этот скилл — операционный слой: команды, процедуры, неочевидные факты репозитория. Правки не должны нарушать ядро доверия проекта: проценты автоматизации только из диапазонов таксономии, архитектура только из каталога блоков, каждая стадия валидируется Pydantic-схемой.

## 1. Карта репозитория

| Путь | Что это |
|---|---|
| `app/main.py` | FastAPI: `POST /blueprint` (живой прогон, rate-limit 5/24ч/IP), `POST /report` (blueprint → текстовый отчёт, без LLM), `GET /` (фронт), `GET /examples[/{name}]`, `GET /config/blocks`, `GET /config/taxonomy` |
| `app/pipeline/stage1..4_*.py` | 4 стадии пайплайна; ретраи на невалидный JSON — внутри каждой стадии |
| `app/pipeline/prompts.py` | Все промпты; taxonomy/catalog подставляются из конфигов, не дублируются текстом |
| `app/pipeline/errors.py` | `PipelineStageError` — наружу отдаётся JSON со стадией, без traceback |
| `app/schemas.py` | Единый источник правды: Pydantic-модели Blueprint и всех стадий. Stage 2/3 — динамические модели, собираются через `build_stage2_models()` / `build_stage3_models()` из конфигов |
| `app/llm_client.py` | Клиент ProxyAPI (OpenAI-совместимый); модель/base_url/параметры — только из окружения |
| `app/render/mermaid.py`, `app/render/report.py` | JSON → Mermaid-диаграммы; JSON → клиентский отчёт (детерминированный, без LLM) |
| `app/static/index.html` | Фронт, одна страница. Список кейсов **динамический** из `GET /examples` — при добавлении кейса не правится |
| `config/taxonomy.yaml`, `config/block_catalog.yaml` | Редактируемые без правки промптов |
| `examples/raw/` | Исходные тексты всех 8 кейсов |
| `examples/extracted|classified|architecture/` | Промежуточные выходы — **только для example_1 и example_2_ambiguous**. Для кейсов 3+ промежуточные артефакты не создаются (решение проекта) |
| `examples/blueprints/` | Финальные Blueprint'ы всех кейсов — вход фронтенда и офлайн-тестов |
| `tests/` | См. раздел «Тесты» — два разных класса |
| `.github/workflows/ci.yml` | CI: ruff (E9,F63,F7,F82) → офлайн-тесты (schemas+render) → docker build. Живых LLM-тестов в CI нет |
| `docs/screenshot-*.png` | Скриншоты README |
| `tmp_*` в корне | Рабочие раннеры/логи отладки — игнорируются `.gitignore`, не коммитить |

## 2. Запуск сервиса

```powershell
pip install -r requirements.txt
copy .env.example .env    # заполнить LLM_API_KEY (шаблон — .env.example)
python -m uvicorn app.main:app --port 8000
```

- Фронт: `http://localhost:8000/`. Живой прогон POST /blueprint — 20–60 с.
- Проверка живости **без расхода LLM**: `GET /config/taxonomy`, `GET /examples`.
- Rate-limit POST /blueprint: 5 запросов/24ч с IP, счётчик **in-memory** — перезапуск uvicorn обнуляет окно.
- Windows: для кириллицы в консоли ставить `PYTHONIOENCODING=utf-8` (в PowerShell: `$env:PYTHONIOENCODING='utf-8'`).
- Деплой — `docker compose up -d --build` (детали в README «Deploy»; один воркер — не масштабировать, лимитер in-memory).

## 3. Тесты: офлайн vs живые

**Офлайн (без LLM, сети и ключа) — прогонять после любых правок:**

```powershell
python -m pytest tests/test_schemas.py tests/test_render.py tests/test_report.py
```

- `test_schemas.py` — фикстуры `examples/` через схемы всех стадий + guard'ы: % вне диапазона категории, неизвестные категория/блок, непокрытый шаг, placeholder без assumption.
- `test_render.py` — Mermaid-рендер, print-only: смотреть глазами, запускать с `-s`.
- `test_report.py` — правила клиентского отчёта (с ассертами).

**Живые (платные вызовы ProxyAPI, ручной запуск):**

- `tests/test_pipeline.py` — по стадиям; print-only **без ассертов** (конвенция: выход LLM смотрим глазами). `-k stage2` / `-k example_2` — фильтры.
- `tests/test_api.py` — e2e POST /blueprint, ~4 вызова на пример; фиксирует каноническую конфигурацию Stage 1 (gpt-4.1, t=0.1) сам.

```powershell
python -m pytest -s tests/test_pipeline.py            # или tests/test_api.py
```

## 4. Как вносить правки

- Каждую стадию менять и тестировать отдельно от общего пайплайна.
- Категории и блоки — enum из конфигов; значение вне списка = ошибка валидации, не «сойдёт».
- Промпты не дублируют taxonomy/каталог — подставляют из YAML.
- Все текстовые/YAML файлы читать с `encoding='utf-8-sig'` (BOM от Windows-инструментов).
- Схема в `app/schemas.py` — единый источник правды; фронт, рендеры и все стадии завязаны на неё. Изменение схемы = проверка всех consumers.
- Скрипты отладки — `tmp_*.py` в корне (в git не попадут); рабочие решения переносить в `tests/` или код.
- Стиль коммитов из истории: префикс области + описание по-русски — `app:` / `docs:` / `examples:` / `tests:`.
- Фронт: палитра/типографика лендинга; при смене оформления — переснять скриншоты README.

## 6. Добавление демо-кейса — установленная процедура

1. Raw-текст: `examples/raw/example_N_<slug>.txt`. Стиль существующих кейсов: конкретные объёмы, «всё вручную», **явные** условия ветвления («если сложное — руководителю») — Stage 1 детектирует только явные.
2. **Два живых прогона** через `POST /blueprint` (не по стадиям), выбрать лучший. Критерии отбора: категории по смыслу (не путать маршрутизацию/переговоры/эскалацию/суждение), risks называют конкретные пробелы текста, HITL соответствует низким %, mvp_scope без артефактов форматирования (префиксы «Шаг N:», суффиксы «(step_N)» — чистить или браковать прогон).
3. **Не создавать** `extracted/`, `classified/`, `architecture/` для нового кейса — только финальный blueprint в `examples/blueprints/`.
4. README: счётчик кейсов в двух местах (раздел 5). `index.html` не правится.
5. Rate-limit: на 2 кейса × 2 прогона (4 запроса) хватает при свежем uvicorn; между кейсами учесть лимит 5/24ч.

## 7. Чек-лист перед публикацией/показом

1. `ruff check app tests --select E9,F63,F7,F82` — как в CI (ruff 0.16.8).
2. Офлайн-тесты (раздел 3) зелёные полностью.
3. Если менялись промпты/стадии/конфиги — прогнать живые кейсы заново и убедиться в стабильности между запусками (CLAUDE.md требует перед показом кому-либо; платно, запускать вручную).
4. `git status` чистый, `tmp_*` не в коммите.
5. README соответствует фактам (раздел 5), после push — CI зелёный.
